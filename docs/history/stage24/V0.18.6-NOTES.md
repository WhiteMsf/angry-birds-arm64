# v0.18.6 — drive the original screen→world→physics input conversion

v0.18.5 identified the real Stage 17 selection failure.

Immediately before calling original `updateGame()`:

```text
body            = (-12.35, -8.473571)
Lua object      = (-12.35, -8.473571)
cursorPhysics   = (-12.35, -8.473571)
cursorWorld     = (-12.35, -8.473571)
cursor screen   = (100, 100)
```

Immediately after original `updateGame()` rejected selection:

```text
cursorWorld     = (100, 100)
cursorPhysics   = (5, 5)
physicsToWorld  = 20
```

So the previous Stage 17 harness was feeding the wrong layer.

The native platform supplies the **screen cursor**. Original gameplay code
recomputes `cursorWorld` and `cursorPhysics` from that screen point before the
bird hit-test. Writing `cursorPhysics` directly before `updateGame()` was
therefore overwritten.

## v0.18.6 fix

Under the current intentionally-headless identity camera, the observed
conversion is:

```text
cursorWorld   = cursorScreen
cursorPhysics = cursorWorld / physicsToWorld
```

Therefore the harness now feeds:

```text
cursorScreen = desiredPhysicsPoint * physicsToWorld
```

For the frame-62 bird position this is approximately:

```text
physics = (-12.35, -8.473571)
screen  = (-247.0, -169.47142)
```

The negative screen coordinate is an artifact of the headless identity camera:
the real game camera would translate that world location into the visible
480x320 viewport. Camera rendering remains outside Stage 17.

The headless pause-button extents are moved to `-1e9` so this synthetic
negative screen coordinate cannot accidentally trigger UI.

The same inverse mapping is used for PRESS, DRAG and RELEASE.

No direct launch transform/velocity/impulse was added. Original `updateGame()`
must still:
- convert screen input;
- select the bird;
- compute rubber-band state;
- release it;
- call reconstructed `applyImpulse()` itself.
