# v0.22.1 — wait for the original LBUTTON route to reopen

v0.22 successfully completed shots #1 and #2, and original Lua prepared
`RedBird_3` at frame 307.

At frame 308 the harness pressed immediately because:

```text
birdReady=true
currentBirdName='RedBird_3'
```

but original `updateGame()` returned:

```text
selectedBird=nil
dragStarted=false
```

even though the cursor was exactly on RedBird_3 (`distance=0`).

This is not a coordinate failure.

## Exact reason

Recovered `updateGame` bytecode routes LBUTTON like this:

```text
if flyingBird == nil:
    go to sling/tap drag setup
elseif birdSpecialtyAvailable:
    process the currently flying bird's specialty path
else:
    go to sling/tap drag setup
```

At the third-shot boundary, `RedBird_2` was still the active `flyingBird`.
The next bird can already be `birdReady=true` before the previous flying
bird has relinquished LBUTTON.

v0.22.1 therefore changes only the synthetic player's timing:

```text
wait for birdReady/currentBirdName
AND
(flyingBird == nil OR birdSpecialtyAvailable == false)
then PRESS
```

It does not write `flyingBird`, `birdSpecialtyAvailable`, `birdReady`,
`currentBirdName`, or any launch/physics state.

A one-shot diagnostic line records when the harness is waiting because the
previous flying bird still owns LBUTTON.
