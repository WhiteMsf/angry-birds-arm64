# v0.26.112 — Stage 24.33.0 — createCircle Lua Metadata Reconstruction

## Evidence from the v0.26.111 live run

- Human 1-10 (`Level8`) loaded with `SmallBlueBird`.
- Two-pointer pinch reached the Android bridge and the untouched `doItAllCamera()` consumer; `worldScale` followed `zoomLevel`.
- A tap while Blue was flying set `birdSpecialty=CLUSTER_BOMB`.
- Untouched `updateGame()` stopped at PC 891: `bad argument #6 to createCircle (number expected, got nil)`.
- The bytecode immediately before that call loads argument #6 from `flyingBird.density`, followed by `flyingBird.friction`, `restitution`, `controllable`, and `z_order`.

## Root cause

The reconstructed ARM64 `createCircle` already consumed all ten Lua arguments to create the Box2D body and native render metadata, but `create_lua_object_circle()` only mirrored `name`, `sprite`, `x`, `y`, and `radius` into `objects.world[name]`. The physical/render template fields therefore disappeared from the Lua representation after level creation. Red never needed to read them back; Blue's original specialty does.

## Fix

Every generic `createCircle` object now also receives:

- `density`
- `friction`
- `restitution`
- `controllable`
- `z_order`

The values come directly from the same call arguments already consumed by the native body/render path. No bird name is inspected.

## Original specialty ownership

The `CLUSTER_BOMB` branch remains untouched Lua. Static bytecode shows this version creates three child circles named `<flyingBird.name>a`, `b`, and `c`, then copies gameplay metadata and assigns their trajectories. No native Blue split exists in this stage. The same physical template fields are also consumed by later specialty code such as `DROPPABLE_EGG`, so this is a general object-contract repair rather than a Blue workaround.
