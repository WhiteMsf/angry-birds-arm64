# v0.26.13 — Stage 24.10 original `loadLuaFile` / `starTable` namespace

The v0.26.12 device run closed the font blocker: `loadFonts()` created the active 480x320 bitmap fonts and post-level `res.useFont(FONT_BASIC)` resolved exactly. The next original Lua instruction then failed because `starTable` was nil.

## Recovered ARMv7 mechanism

`GameLua::loadLuaFile(path, tableName)` has two branches. When `tableName` is non-empty it constructs a fresh `lua::LuaTable`, calls `LuaTable::read()` on the file, then installs that table under `tableName`. `LuaTable::read()` compiles the chunk with that fresh table passed into `LuaState::compile`; `handleLoadResult()` pushes the table, calls `setFEnv()` on the loaded function, then executes it. When the name is empty, the chunk is read directly into the root GameLua table.

This explains the historical Stage24 mismatch: it executed `starLimits.lua` directly in `_G`, producing individual `Level*` globals, while original result logic expects `starTable[levelName]`.

## What changes

- `starLimits.lua` no longer executes in `_G`.
- The Stage24 loader reproduces the original non-empty-table-name environment semantics and installs the populated table as `starTable`.
- No star thresholds are synthesized in C++; values come from the user's untouched local 1.4.2 `starLimits.lua`.
- Startup audits `starTable` and Level1's `silverScore`, `goldScore`, and `eagleScore`.
- Post-level logging includes live Level1 thresholds.
- Font bootstrap, physics, touch, persistence, menu bootstrap and post-completion quarantine are retained.

The visible result screen and glyph rendering are still intentionally not implemented in this stage.
