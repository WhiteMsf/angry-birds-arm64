# v0.26.132 — Stage 24.42.1
## Nonlegacy deferred bird velocity + glass/wood gravity/contact audit

The first Danger Above / Boomerang run reached 6-5 (`LevelP3_224`) and proved
that the untouched Lua `BOOMERANG` specialty itself was already functional:
the original branch published `boomerangActive`, switched to
`BIRD_BOOMERANG_SPECIAL`, and drove the existing generic native `applyForce`.

The fatal boundary happened later, when `BoomerangBird_1` destroyed a wood
block. Stage 16 deliberately failed closed whenever a controllable bird lacked
a Boolean `useLegacyCollisionPath`, because the alternate destruction branch
had not yet been recovered.

The retained ARMv7 `GameLua::BeginContact` disassembly now closes that branch:

- `0x57898..0x578A8`: `(collisionForce - strengthBefore) / collisionForce`
- `0x578AC..0x578B0`: multiply by `velocityMultiplier`
- `0x578BC..0x578C4`: upper-clamp to `1.0f`
- `0x578C8..0x578EC`: write scaled x/y velocity into `RenderObjectData`
- `0x578E8`: set `RenderObjectData+0x84 pendingVelocity = true`
- `0x578F0 -> 0x57810`: disable current contact

Unlike the legacy branch, the alternate path does not immediately call
`setVelocity` from inside `BeginContact`. The ARM64 reconstruction therefore
keeps a per-object deferred velocity slot and consumes it after the fixed
Box2D Step / stock `removeBlocks()` boundary, before render-history capture
and before any later fixed Step. No Boomerang- or level-specific branch is
introduced.

This stage also adds a passive glass/wood physics audit requested from an
earlier video-vs-port discrepancy where glass appeared attached to wood before
physics/gravity became active and the discrepancy disappeared once simulation
started. The audit does not change physics. It records:

- the false->true physics-enable boundary and world gravity;
- all wood/glass body positions, velocities, angles, awake/active states,
  dimensions and first-fixture friction/restitution/density before the first
  Step and for the first 12 fixed Steps;
- wood<->glass BeginContact/EndContact transitions;
- touching/enabled/manifold-point state for live wood/glass contacts.

The goal is to distinguish initial placement/render state, contact generation,
sleep/wake behavior, and fixture/contact differences before changing any
physics constant.
