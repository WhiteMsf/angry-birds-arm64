# v0.26.15 / Stage 24.12 — original prepareMenuPage + BitmapFont metrics

The v0.26.14 live run proved the recovered Level1 selection context: `levelName='Level1'`, the original `starTable.Level1` thresholds were available, the highscore entry was created, the result page became `currentMenu=levelComplete`, and physics was disabled. The next fault was `attempt to perform arithmetic on field 'width' (a nil value)`.

Static audit found the direct cause in the Stage24 harness: after loading the untouched gamelogic bytecode it still replaced the original Lua `prepareMenuPage()` closure with a historical no-op. The original result flow therefore activated `levelComplete` without the width/height/text layout fields that `prepareMenuPage()` normally computes.

Stage 24.12 removes that replacement and verifies that `prepareMenuPage` is still an original Lua closure. To support the original layout function without invented dimensions, this stage also reconstructs the ARMv7 bitmap-font metric boundary from the untouched 480x320 font DATs already sourced by the local build:

- legacy and `KA3D/FONT` v1 font containers;
- font image UTF entry (parsed but not rendered yet);
- leading and tracking;
- glyph code/rectangle records and glyph widths;
- max ascending / max descending metrics;
- `res.getStringWidth`, `res.getFontLeading`, `res.getFontHeight`, tracking and max metrics.

`GameLua::clipText(group,id,width)` is restored as a native bridge using the selected original bitmap-font metrics and `TEXTS_BASIC` localization. It publishes the original `clippedText.widestLine` and `clippedText.lines` shape consumed by the untouched Lua `prepareTextItem()`.

The original `updateMenu` state machine is left intact. `drawMenu` remains intentionally headless in this stage so the run can prove the result-mode transition and layout without inventing presentation or requiring menu texture payloads. New telemetry reports the actual `currentGameMode` closure and the prepared `levelComplete.width/height` once it reaches `updateMenu`.

This is still not a visual result-screen implementation. The next presentation slice should restore the original `drawMenu` path with locally sourced original menu PVR payloads after the logical result flow is stable.
