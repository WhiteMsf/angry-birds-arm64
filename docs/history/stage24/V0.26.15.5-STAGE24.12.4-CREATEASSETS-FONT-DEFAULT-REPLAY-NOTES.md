# v0.26.15.5 / Stage 24.12.4 — exact createAssets font-default replay

## First divergence from v0.26.15.4

The Stage 24.12.3 audit showed that `prepareTextItem` is behaving correctly: when
`item.font == nil`, it assigns `defaultMenuFont`, then calls `setFont(item.font)`,
then `clipText(...)`.

The failure occurred because Stage24 replayed `loadFonts()` out of `createAssets()`
but omitted the next two original instructions. Therefore `defaultMenuFont` stayed
nil and `setFont(nil)` reached the native `res.useFont` bridge with no current font.

## Recovered original bytecode semantics

The untouched `createAssets` prefix is:

```lua
loadFonts()
defaultMenuFont = fontBasic
setFont(defaultMenuFont)
```

`setFont` itself is only:

```lua
res.useFont(arg)
```

This is direct bytecode evidence, not a guessed FONT_BASIC fallback.

## Change

After the existing original `loadFonts()` replay, Stage24 now replays exactly:

1. `defaultMenuFont = fontBasic` using Lua C API value assignment;
2. the untouched original Lua `setFont(defaultMenuFont)` closure.

The full `createAssets()` remains intentionally skipped because its tail creates
audio and other systems outside this slice.

No changes were made to:

- `prepareTextItem`;
- `prepareMenuPage`;
- `clipText`;
- `res.useFont` nil/miss behavior;
- font metrics;
- `drawMenu`;
- physics/render/gameplay.

## Expected telemetry

Before `initializeMenu`:

```text
[stage24.12.4-font-default] PASS defaultMenuFont='FONT_BASIC' currentFont='FONT_BASIC'
```

Then the first `prepareTextItem` with no explicit font should call
`setFont(FONT_BASIC)` rather than `setFont(nil)`, allowing `clipText` to use the
already parsed real FONT_BASIC metrics.
