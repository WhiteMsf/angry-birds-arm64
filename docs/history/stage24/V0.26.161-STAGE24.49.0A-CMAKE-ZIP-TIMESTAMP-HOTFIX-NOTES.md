# v0.26.161 / Stage24.49.0A — CMake ZIP timestamp hotfix

## Symptom
The final 1.0 orchestration successfully created/reused the permanent signing key and entered the audited build, but Ninja repeatedly printed `Re-running CMake` with an ever-growing progress denominator and never compiled the target.

## Root cause
Classic ZIP timestamps do not carry a timezone. The project archive is produced in a UTC environment; Windows extraction on a UTC-03 host can therefore assign source mtimes that are ahead of the local clock. If `CMakeLists.txt` is newer than a freshly generated `build.ninja`, Ninja's `RERUN_CMAKE` edge remains dirty forever.

## Fix
Immediately before deleting/recreating `b24`, the build script sets only the filesystem `LastWriteTime` of the root `CMakeLists.txt` to local `now - 10 s`. The file bytes are not modified. Stage24.49.0A's release-engineering contract explicitly checks that this guard remains wired.

## Fidelity/security
- `stage24_live_surface.cpp`: unchanged.
- `CMakeLists.txt` bytes: unchanged; frozen SHA-256 must still match the v0.26.157 baseline.
- Existing `~/.angry-arm64/signing/angry-birds-release.p12`: reused, never regenerated when present.
- No private signing material is copied into the project or distribution tree.
- Historical save backup behavior is unchanged.
