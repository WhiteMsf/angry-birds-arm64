# v0.26.36 — Stage 24.16.1

## Native Android resolution ownership audit

### Status
Diagnostic-only. Gameplay remains visually identical to v0.26.35 on purpose.
The 480x320 gameplay viewport / black physical matte is retained as the known
harness baseline until the untouched ARMv7 binary tells us what owns Android
screen dimensions.

### What Stage 24.16.0 proved
The returned diagnostics close several questions without yet closing the native
resolution boundary:

- the current 480x320 gameplay pillarbox is explicitly a Stage24 harness policy,
  not evidence of original Android behavior;
- untouched `selectAssetProfile` has Android MENU/COMPOSPRITES buckets
  `320x240_android_partial`, `480x320_android_partial`, and `864x480` selected
  from `screenHeight`, while the INGAME family falls through to `864x480` on the
  normal Android branch;
- untouched `selectFontProfile` similarly has 320x240 / 480x320 / 864x480 Android
  buckets;
- original camera code consumes `screenWidth` and `screenHeight` directly when
  computing the visible world rectangle, so changing those globals is not a
  cosmetic resource-selection change;
- `initCameras` compares stored camera-profile aspect against current
  `screenWidth/screenHeight` and rescales camera data when the aspect differs.

### Audit gap found in Stage 24.16.0
The original symbol table already exposed:

- `gr::EGL_Context::setViewport(gr::Rect const&)`
- `gr::EGL_Context::viewport() const`
- `math::float4x4::setScreenTransform(...)`
- `framework::AndroidOSInterface::setResolution(int, int)`
- `framework::App::resolutionChanged()`
- `gr::Context::transformPointToScreen(int&, int&) const`
- imported `glViewport`

However the Stage24.16.0 *exact-body* regex looked mostly for `gr::Context::*`, so
several of the most important concrete symbols were inventoried but never
actually disassembled. Stage24.16.1 fixes the auditor rather than inventing a
runtime answer.

### New static report
`stage24.16.1-native-resolution-ownership.txt`

Generated directly from the user's untouched ARMv7 `libangrybirds.so`. It:

1. inventories resolution / display / EGL ownership symbols;
2. disassembles the exact native bodies for the concrete viewport, screen
   transform, Android resolution, resolution-changed and point-to-screen
   methods;
3. includes EGL / Android interface constructors when symbolized;
4. scans the complete disassembly for direct BL/BLX callers of those methods and
   `glViewport`, emitting compact caller contexts rather than a multi-kilometre
   dump;
5. emits focused GameLua-constructor calls that may reveal where Lua screen
   globals are registered or sourced.

Indirect virtual calls remain explicitly unresolved instead of being guessed.

### New live selector matrix
`stage24.16.1-selector-matrix.txt`

Before native bindings replace any original Lua names, the untouched
`selectAssetProfile` / `selectFontProfile` closures are evaluated at a small
resolution matrix spanning 240-, 320-, 480-, 720-, 800- and 1080-high screens.
For every row the report records INGAME, MENU, COMPOSPRITES, SPLASHES and FONT
returns.

`screenWidth` and `screenHeight` are restored after the matrix. No camera
function is called and no runtime presentation dimension is promoted from a
probe row.

### Decision gate
Do not remove the pillarbox yet. The next implementation is allowed only after
this report identifies one of these original ownership models from ARMv7
behavior:

- native full-surface dimensions feed Lua and viewport directly;
- native dimensions are normalized to a logical height/width before Lua;
- viewport and Lua camera dimensions intentionally differ;
- or another original rule visible in the binary.

No `999x480`, `864x480`, `800x480`, physical-surface aspect, or screenshot fit is
accepted merely because it looks plausible.
