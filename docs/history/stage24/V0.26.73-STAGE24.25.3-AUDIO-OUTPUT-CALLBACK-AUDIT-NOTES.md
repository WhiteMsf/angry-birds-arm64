# v0.26.73 / Stage 24.25.3 — audio output callback audit

This stage is diagnostic-only. It does **not** change Lua audio ownership, alias/group selection, WAV decoding, volume rules, tracks, handles, or the Stage24.25.2 OpenSL playback policy.

The previous runtime proved:

- untouched `createAssets()` audio replay: PASS (`createCalls=184`, `wavLoaded=166`, `groups=27`),
- supported WAV requests reach the backend as real `PLAY` calls,
- the OpenSL player reports successful construction,
- the device was nevertheless subjectively silent.

Stage24.25.3 therefore instruments the boundary between our software mixer and Android's OpenSL output:

- decoded peak amplitude per requested clip (`clipPeak`),
- peak amplitude of both buffers primed before `SL_PLAYSTATE_PLAYING`,
- `SLPlayItf::GetPlayState`,
- Android simple buffer queue `count/index`,
- callback invocation/enqueue counts,
- per-callback mixed PCM peak,
- active voice count at output snapshots.

Interpretation is deliberately mechanical:

- `clipPeak > 0` proves the WAV payload decoded to non-silent PCM;
- `primePeak* > 0` or callback `peak > 0` proves our mixer produced non-silent stereo PCM;
- `playState == SL_PLAYSTATE_PLAYING` + successful queue state + non-zero PCM isolates any remaining silence below the mixer boundary;
- callbacks remaining at zero after playback isolates the failure to the OpenSL buffer-queue lifecycle instead.

No synthetic tone and no replacement audio API are introduced in this stage.
