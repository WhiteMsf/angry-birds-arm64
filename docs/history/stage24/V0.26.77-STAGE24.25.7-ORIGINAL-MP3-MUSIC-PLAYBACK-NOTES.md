# v0.26.77 — Stage 24.25.7 — original MP3/music playback

## Evidence gate closed by Stage 24.25.6

The untouched ARMv7 `AudioClipInstance::fetchData(void*, int)` finally closes the EOF/loop ownership boundary that blocked MP3 playback:

- `AudioClipInstance` is 28 bytes in the recovered mixer path.
- `+0x18` is the loop byte supplied by `AudioMixer::playClip(..., bool loop, ...)`.
- `+0x1a` is the ended byte used by `getPlayingClipCount`, the mix paths and `flushQueueAndRemoveEndedClips`.
- `fetchData()` first consumes an optional `AudioBuffer` (`+0x8`); otherwise it calls the clip's virtual fetch path, which resolves to `AudioClip::getData(..., AudioClipCursor*)` and then `AudioReader::readData`.
- A zero-byte fetch is EOF.
- On EOF with loop=false, `fetchData()` sets `+0x1a = 1` and returns the number of bytes already filled.
- On EOF with loop=true, it writes zero to the cursor fields at `+0x8` and `+0x0c`, then continues filling the same caller request from the beginning of the clip.
- `flushQueueAndRemoveEndedClips()` removes instances whose `+0x1a` is set; `getPlayingClipCount()` does not count ended instances.

This means loop/EOF/handle lifetime no longer needs to be guessed from Android behavior.

## Stage 24.25.7 implementation

The original Lua still owns:

- `createAssets()` and all 184 `createAudio` calls;
- `audioGroups` construction and random variant selection;
- `playAudio(name, volume, loop, track)` calls;
- stop/query calls and the numeric-handle contract;
- track/master volume behavior, including the ARMv7-proven track clamp `[0,1]`;
- the intentionally odd positive `audioRampVolume` lifecycle recovered in Stage24.25.5.

WAV behavior from Stage24.25.2 is unchanged.

For the 18 original MP3 assets, Stage24.25.7 adds an ARM64 compatibility decoder using Android NDK `AMediaExtractor` + `AMediaCodec` (`audio/mpeg`). The original 1.4.2 ARMv7 binary used mpg123; this stage does **not** claim bit-identical decoder internals. The compatibility decoder's only job is to produce signed PCM from the user's original MP3 bytes. That PCM then rejoins the same recovered software-mixer path already used by WAV.

All MP3s are registered cheaply during the untouched `createAssets()` replay. Decode is lazy on first `playAudio()` request. After decode:

- the clip uses the same per-voice `frame` cursor as WAV;
- loop=true rewinds the cursor at EOF and continues playback;
- loop=false marks the voice inactive at EOF;
- `isAudioPlaying(handle/name)`, `stopAudio(name)`, `stopAllAudio`, track volume and master volume remain shared with WAV;
- no MP3/WAV payload is included in the project ZIP; the build copies the user's own extracted assets into the APK.

The aapt command now explicitly uses `-0 mp3`, because NDK `AMediaExtractor_setDataSourceFd()` requires direct FD access and compressed APK assets cannot provide one through `AAsset_openFileDescriptor()`.
