# v0.26.8 — Stage 24.5 original menu sprite metadata bootstrap

## Evidence from v0.26.7

The `levelPath` bridge is active, and `createMenuPages()` advances from PC 496 to PC 523.
The next failure is no longer a missing platform path: `res.getSpriteBounds()` cannot resolve
`LS_LEVEL_BG_NORMAL_OPEN_1`.

The Stage24 SpriteDB had only loaded `INGAME_BLOCKS_1.dat` and `INGAME_BIRDS_1.dat`.
The original 864x480 asset tree also contains the three sprite sheets named directly by the
original `createMenuPages` bytecode: `LEVELSELECTION_SHEET_1`, `BUTTONS_SHEET_1`, and
`POPUPS_SHEET_1`.

## Change

The build script locally stages only the `.dat` SPRT metadata from those three sheets; the
bootstrap archive itself still does not contain the user's original runtime image data. At
runtime those metadata files are materialized into the app-private Stage24 directory and
loaded into the same `SpriteDB` before the original `initializeMenu()` probe runs.

A hard gate verifies that `LS_LEVEL_BG_NORMAL_OPEN_1` resolves and logs its recovered sheet,
size, and pivot. Missing sprite errors now also include the bundle/sheet argument passed by Lua.

This stage still does not render the result/menu textures. It only restores the metadata
surface required for the original Lua menu tables to be constructed.
