# v0.26.80 — Stage 24.26.1 Native Trajectory Renderer & Puff Contract Audit

## Why this pass exists

Stage 24.26.0 closed the producer/storage side far enough to stop guessing:

- `addToTrajectory(slot,x,y)` and `addPuffToTrajectory(slot,x,y)` address separate `lang::Array<math::float2>` families;
- three slots are selected by `slot=1..3`;
- two banks are selected by the native `GameLua` bank field;
- `startNewTrajectory()` flips the bank and clears the newly selected three normal + three puff arrays;
- untouched Lua samples normal flight only after the previous Lua trajectory point is more than 20 world units away;
- Level 1-1 exercised real normal ADD/START sequencing but no puff producer.

The missing half is the **consumer**: which untouched ARMv7 routine reads those arrays, where that occurs relative to `GameLua::drawGame()`, which exact `TRAIL_*` resources are selected, and what the four original puff callsites mean.

This revision remains deliberately **diagnostic-only**. It does not store or draw trajectory pixels on ARM64.

## New native audit

`tools/stage24261_trajectory_renderer_puff_contract.py` emits:

`stage24.26.1-trajectory-renderer-puff-contract.txt`

against the user's untouched 1.4.2 ARMv7 library and asset tree.

It performs a full `llvm-objdump -d --demangle` rather than trusting the ELF-reported `GameLua::drawGame()` size, because prior Stage 23.6C work proved that the symbol-size boundary can truncate the real draw tail.

The report includes:

- the complete untouched `GameLua::drawGame()` body and direct call sequence;
- every disassembled function that touches the recovered trajectory/puff layout offsets:
  - normal Array family: `+0x1B4/+0x1B8/+0x1BC`;
  - puff Array family: `+0x1FC/+0x200/+0x204`;
  - bank selector: `+0x244`;
- bounded instruction contexts around those field touches, ranked toward draw/render owners while retaining the known storage writers as control evidence;
- exact retained `TRAIL_WHITE_*`, `TRAIL_BLACK_*`, `TRAIL_FLOWER_*`, and tutorial-trail strings;
- ELF32 file-offset → virtual-address mapping for those strings plus exact 32-bit pointer words when present;
- opportunistic disassembly contexts that mention the string/pointer addresses directly;
- neighboring original DAT metadata strings around every trail resource;
- original script strings around `birdSpecialty`, `addPuffToTrajectory`, and `BIRD_*_SPECIAL` material.

An empty direct string-address-xref section is not a failure: the original Android binary is position independent and may reach resources through GOT/owner objects rather than literal absolute addresses. The field-consumer scan is the primary renderer-owner probe.

## New untouched Lua puff audit

Before the native bindings are replaced, the live ARM64 bridge now performs a second read-only dump of the untouched `updateGame` Proto.

New tags:

```text
[stage24.26.1-puff-lua]
[stage24.26.1-puff-bytecode]
[stage24.26.1-puff-constant]
```

Unlike the Stage 24.26.0 bytecode printer, this one explicitly resolves RK constants used by `EQ/LT/LE` and arithmetic instructions. That means branches such as:

```text
birdSpecialty == K[...]
```

are no longer left as opaque `C=455`-style operands: the corresponding constant value is printed beside the instruction.

Every `addPuffToTrajectory` use in untouched `updateGame` gets a wide producer window plus a bounded constant-table neighborhood. This is intended to identify the exact specialties that produce puff trajectory without requiring a particular bird to be exercised during the standard test.

If a real puff call does occur, an additional runtime line records:

```text
birdSpecialty
flyingBird.name
flyingBird.definition
flyingBird.sprite
Lua callsite / PC
```

The binding still returns no values and stores/draws nothing.

## Validation run

Build/install:

```powershell
powershell -ExecutionPolicy Bypass -File .\build-stage24-live-surface-touch-arm64.ps1
```

Standard regression path:

1. Enter Level **1-1**.
2. Pull and launch one Red normally.
3. Let it hit wood/ground.
4. Leave the level alive for a few seconds after the first impact.
5. No need to complete the level.

A runtime `PUFF` call is **not required** for PASS in this pass. If one naturally occurs while testing another unlocked level, it is useful extra evidence but should not be forced at the cost of changing the audit target.

Collect:

```powershell
powershell -ExecutionPolicy Bypass -File .\pull-stage24-live-log.ps1
```

## Decision gate

Do **not** implement the visible dotted trajectory until report review establishes, from original evidence:

1. the actual reader(s) of both recovered buffer families;
2. whether both banks are drawn simultaneously and in what order;
3. where the trajectory consumer sits relative to the recovered gameplay draw passes;
4. exact resource selection among the original `TRAIL_*` assets;
5. any scale/alpha/fade/transform policy owned by the native consumer;
6. the specialty mapping and role of the puff buffers.

Audio and all previously closed Stage 24 behavior remain frozen.
