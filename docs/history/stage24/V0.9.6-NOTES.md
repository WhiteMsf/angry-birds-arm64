# v0.9.6 — reconstruct Android -> level camera-profile bridge

v0.9.5 located the stripped-bytecode crash exactly:

- function: `animateBirdToSlingShot`
- PC: 190

Static disassembly around PC 190 is:

```text
186 GETGLOBAL objects
187 GETTABLE  birdCameraData
188 GETGLOBAL deviceModel
189 GETTABLE  [deviceModel]
190 GETTABLE  px          <-- nil access
```

The same pattern immediately follows for `py` and for `castleCameraData`.

The original `Level1.lua` camera tables contain concrete subprofiles named
`iphone` and `ipad`; the phone profile is explicitly 480x320. Across the
original level corpus there are no literal `android` camera-profile keys,
while the original `selectAssetProfile()` Lua function *does* have an explicit
`deviceModel == "android"` branch. This means a platform/profile bridge is
required somewhere outside the pure level chunk.

Stage 8's reconstructed native `loadLevel(String)` is exactly such a boundary.

v0.9.6 therefore:

1. sets `deviceModel = "android"` so the original Android Lua branches see the
   correct platform identity;
2. after executing the original level chunk, but before publishing
   `loadedObjects`, aliases:
   - `birdCameraData.android` -> original `birdCameraData.iphone`
   - `castleCameraData.android` -> original `castleCameraData.iphone`
3. does this by table reference only; no original camera numbers are modified.

For the current 480x320 Stage 8 viewport, the original `iphone` table is the
matching phone camera profile.

The exact VM PC tracer from v0.9.5 remains enabled near the frame-61 boundary,
so any next stripped-Lua dependency will again identify its function and PC.

No Box2D, Level1 object, timer, bird, update(), updateGame(), or gameplay
physics behavior was changed.
